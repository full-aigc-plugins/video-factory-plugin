## Context

参见 `proposal.md`。既有边界：素材必须落在授权根内、必须携带哈希与授权信息、不接受 URL 作为 asset path、不自动安装软件、不承担图片生成或 Blender 控制（`skills/video-factory-use/SKILL.md` 的"不做"清单）。本变更只增加"如何获得素材"的判定纪律，不改变这些边界。约束：技能文档主体属上游受管，插件本地只能做交叉引用。

## Goals / Non-Goals

**Goals:**

- 让"素材从哪来"成为一次有依据、可审计的显式判定，而不是 agent 的默认省事选择。
- 让"素材质量不足"这类失败在计划阶段就有一个对抗手段，而不是等到判定阶段才发现无门可依。
- 复用 `AssetManifest` 已有字段承载决策记录，不新增 schema。

**Non-Goals:**

- 不改变素材的授权与哈希边界，运行时行为不变。
- 不在插件内实现任何素材生成能力（不生成图片、不驱动 Blender、不调用生成 API）。
- 不移植 dream-loop 的模型分层与自循环。
- 不移植 dream-loop 对 Blender 的否定性结论。
- 不引入付费路径：任何生成式调用仍由用户在插件之外完成并把带哈希的授权产物送入计划。

## Decisions

1. **阶梯为四级且顺序固定：外部下载 → 生成式 image-to-3D/图像 → 本地建模 → 程序化。** 移植自 dream-loop。顺序的理由是把"现成的最好"放前面、"完全靠代码凑"放最后，因为逆序（先程序化）在主观上总是"更快"，而质量差距不可逆。

2. **每级都要求记录"为什么进入下一级"。** 单纯规定顺序不足以对抗走捷径：agent 可以声称"找不到"就跳到程序化。因此要求把不可用的具体原因写入素材记录（`source`/`license` 字段已有的承载能力）。这是本变更可审计性的核心。

3. **程序化必须给出非时间性理由。** 明确不接受"因为快""因为省 token""因为时间紧"作为理由。移植自 dream-loop 的"Don't do this to save time or reduce complexity. Do it only because it is either the only remaining option, or because it truly is the option that produces the best-looking result"。

4. **明确区分"下载网络素材"与"用生成模型产出素材"。** dream-loop 特别澄清后者不算前者，且即使用户说"不要下载网络素材"也仍可用生成式。保留这一区分，避免授权边界被理解过宽或过窄。注意本插件的边界更强：插件自身不调用生成 API，生成发生在插件之外，产物以带哈希的授权文件形式送入。

5. **不移植"不要用 Blender"这一结论。** dream-loop 的 Plus 模式主张 Blender 太慢太贵，与本生态 `blender-design` 插件（提供 MCP 与脚本化建模）正面冲突。本变更改为把"本地建模"作为一个中性级别，由场景复杂度、可用工具与时间预算共同裁定，并在技能文档中说明存在这条冲突，要求 agent 不要无条件跳过该级。

6. **生成式纹理与法线不可用纯色或程序化噪声替代。** 移植自 dream-loop 的纹理纪律：如果具备图像生成能力，纹理、法线、天空盒应由生成式产出而非程序化填充。理由：这一项对"看起来真实"的贡献远大于几何复杂度，且最容易被当作可省略的细节。

7. **阶梯不改变授权边界。** 无论素材来自哪一级，都必须落在授权根内、携带哈希、可被 `registerAssets` 接受；URL 仍不能被直接写入 asset path。

## Risks / Trade-offs

- [阶梯提高单次计划的准备工作量，可能拖慢简单任务] → 阶梯只要求"逐级判定"，不要求逐级尝试；简单任务可以合理地在第一级就说明"用户未授权下载，且不需要生成式素材"，判定成本很低。
- [生成式素材质量不稳定，可能引入比程序化更差的结果] → 要求把生成式产物与目标参考图配对检查（与 `2026-09-21-add-visual-semantic-gate` 的物证机制一致），不达标时回退到更合适的级别。
- [与 blender-design 生态的定位冲突被写入文档后引起混淆] → 文档明确表述为"该级是中性选项，需按场景裁定"，并对需要精细 3D 资产且本机装有 Blender 的场景给出正向指引。
- [上游受管导致文档改动被阻塞] → 先在 `video-factory-harness`（插件本地）落地纪律说明，使纪律即时生效；`video-factory-plan` 的正文随上游 tag 补齐。
- [要求记录理由可能被 agent 用模板化文字敷衍] → 理由必须指向具体的不可用条件（无凭据、被显式禁止、无匹配模型、目标本身不要求细节），不接受泛化表述。

## Migration Plan

1. 在 `video-factory-harness`（插件本地）落地阶梯纪律与交叉引用，立即生效。
2. 上游技能仓改写 `video-factory-plan` 正文，发布新 tag。
3. 本仓执行 `skill_vendor.py update --source-ref video-factory-skills=<tag> --expected-sha <peeled-sha>` 同步，并随 `skills.lock.json` 一起提交以通过受管技能检查。
4. 补文档测试断言（如阶梯级别枚举与"不接受时间性理由"表述存在），bump 版本并同步两仓。
