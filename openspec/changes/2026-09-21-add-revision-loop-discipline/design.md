## Context

参见 `proposal.md`。既有事实：计划有 `round`、台账有单调 `revision` 与合法迁移表、approval 绑定 round 与 quote revision、`diffEditDecision` 能算出 clip 级差异。缺的只是"把上一轮的判定结果保存下来并与本轮比较"这一层。约束：不改人工审批的终审地位，不引入自动循环，不引入自动重试（仓库明令"失败只记录一次，不自动重试"）。

## Goals / Non-Goals

**Goals:**

- 让"改了 N 轮却没进展"和"这轮比上轮更差"在系统里可检测、可报告、可审计。
- 为无限微调提供一个确定性出口，并把最终决定交回人类。
- 复用既有台账与 round 语义，不新增第二套轮次概念。

**Non-Goals:**

- 不实现自动循环：插件不自动发起下一轮，也不自动改计划。
- 不让分数自动推进作业状态——状态推进仍归人工 `accept`。
- 不在插件内实现模型评分（由 `2026-09-21-add-visual-semantic-gate` 提供评分来源）。
- 不在本变更中修改 `run` 的渲染或审批逻辑。

## Decisions

1. **快照写入台账而非独立文件。** 台账已是唯一事实来源且已原子写入，跨轮数据放这里可以与 `revision` 天然对齐，也避免出现第二份需要同步的状态。台账中新增每轮的 `{round, revision, decision, totalScore, gateDigest, gapFingerprint, at}`。

2. **用"缺口指纹"而非自由文本做停滞判定。** 把评审缺口归一化（维度 + 稳定标识）后哈希，得到可比较的指纹。理由：自由文本每次措辞都不同，直接比较会把"同一个缺口"误判成多个新缺口，从而永远检测不到停滞——这正是 dream-loop 用"评审连续两次点出同一缺口"表达同一意图的实现方式。

3. **回归检测只在可比分数之间进行。** 只有两轮都有总分时才比较回归；缺分时退化为比较门状态摘要（是否存在新的 `FAIL`）。理由：避免在评分缺失时用默认值伪造回归信号。

4. **停滞判定采用双条件与固定阈值。** 默认 N=2：(a) 最佳总分连续 2 轮提升不足 1.0 分，或 (b) 同一缺口指纹连续出现 2 次。阈值可配置但必须有默认值。移植自 dream-loop 的"best score hasn't improved by a full point in 2 rounds, or the judge has named the same gap 2 times in a row"。

5. **停滞升级的输出是"建议架构级变更"而非自动执行。** 达到停滞条件时，判定输出必须包含明确结论——停止微调、重新审视整体方案（素材是否足够、镜头职责是否正确、结构是否需要重排）——但仍由 agent 或人类执行，插件不自动改计划。

6. **出口只有人类。** 二次停滞（做了架构级变更仍未脱离停滞）时状态进入 `ReworkReady` 并要求人类裁定，不提供自动继续路径。理由：这与插件既有的"人工 rejected 永远不能被模型覆盖"和"显式人工 accept 才进入 Completed"完全一致，而 dream-loop 的自主循环部分与这两条冲突，故不移植。

7. **不移植 dream-loop 的模型分层路由与自循环。** Plus 模式的"orchestrator 用弱模型驱动强子 agent"会破坏插件的宿主中立性；自循环会绕过人工闸门。

## Risks / Trade-offs

- [阈值过敏感导致正常迭代被误判为停滞] → N 默认 2 且要求"最佳分提升不足 1 分"，而非"分数未升高"；同时把停滞作为 advisory 结论呈现，不阻断人工批准。
- [缺口指纹因维度命名漂移而失效] → 指纹只由受控维度枚举生成，自由文本不参与哈希。
- [跨轮数据使台账膨胀] → 每轮只存摘要（分数、门状态位、指纹），不存完整门列表与评审正文。
- [与 `2026-09-21-add-visual-semantic-gate` 的落地顺序耦合] → 该变更未落地时本变更退化为门状态摘要比较，仍能检测"连续多轮全 PASS 无变化"的空转，功能不空转。
- [技能文档改动受上游受管约束阻塞] → `video-factory-run` 与 `video-factory-recover` 的文档改动须经上游发版；可先落地 `video-factory-harness`（插件本地）与运行时逻辑，文档收口随上游 tag 补齐。

## Migration Plan

1. 台账新增每轮快照字段，向后兼容既有台账（旧台账无快照时视为首轮，不触发任何停滞判定）。
2. 落地缺口指纹与跨轮比较，接入判定输出。
3. 更新 `video-factory-harness`（插件本地可直接改）。
4. 上游发版后同步 `video-factory-run` 与 `video-factory-recover` 的技能文档。
5. 补测试并 bump minor 版本，同步插件仓与市场仓。
