## 0. 这一步为什么必须存在

本仓 9 个技能分属三条不同的所有权链，其中 **5 个是外部托管技能**：

```
skills.lock.json   → full-aigc-skills/video-factory-skills @ ref v1.0.1 / sha 6077533c5dd9c5089998e07c557f6a2d5f6c2203
                     video-factory-use / -plan / -run / -judge / -recover
plugin-local-skills.json → video-episode-slicing / video-factory-harness / video-shots / video-sync
```

由此产生两条硬约束，均已被 CI 固化：

1. **`skills-check.yml` 的 `vendor-check` 作业**在 push main 与 PR 上都会跑 `python3 scripts/vendor/skill_vendor.py check --offline`，逐技能比对 `skills.lock.json` 里的 sha256。改动 `skills/video-factory-judge/**` 任何字节都会让摘要不匹配 → 作业失败。
2. **同一工作流的 PR 步骤 "Reject direct edits to externally managed skills"** 显式扫描 diff 路径，命中托管前缀且未同时改 `skills.lock.json` 时直接 `exit 1`，并提示正确做法是「Edit video-factory-skills, release a new tag, then run scripts/vendor/skill_vendor.py update」。

**推论：任何落在 judge / plan / run / use / recover 五个技能上的文本改动，都不可能在本仓直接落地。** 而当前未提交的 5 个 OpenSpec 变更里，`repair-media-gate-evaluation` 的 §4、`add-visual-semantic-gate` 的 §4/§5.1/§5.3 都写了要改 `skills/video-factory-judge/`。这三处是本方案的直接动因。

#### A2 — 跨仓 dispatch 实测失败：HTTP 403，且本处无法修复

v1.0.1 Release 触发的 `notify-consumers.yml` 运行（run `35461655119`，2026-09-19T18:35:01Z，耗时 9 秒）**失败**，失败步骤是最后一步 `Dispatch immutable release`：

```
RELEASE_SHA: 6077533c5dd9c5089998e07c557f6a2d5f6c2203   ← tag → peeled SHA 解析正确
gh: Resource not accessible by personal access token (HTTP 403)
{"message":"Resource not accessible by personal access token",
 "documentation_url":"https://docs.github.com/rest/repos/repos#create-a-repository-dispatch-event",
 "status":"403"}
```

逐项排除后的定位：

| 检查项 | 实测结果 | 结论 |
|---|---|---|
| secret 是否存在 | `gh secret list --repo full-aigc-skills/video-factory-skills` 列出 `SKILLS_SYNC_TOKEN`（创建于 2026-09-17T10:08:07Z） | ✅ 存在 |
| secret 是否为空 | 运行日志中 `GH_TOKEN: ***`（若为空会展开为空白而非掩码） | ✅ 非空 |
| tag 格式校验 | 已通过 | ✅ 正常 |
| peeled SHA 解析 | `6077533c...` 与实际 tag 一致 | ✅ 正常 |
| 跨仓 dispatch 权限 | 403 | ❌ **根因** |
| 插件侧是否收到过 dispatch | `skills-sync.yml` 历史全是 `schedule` 触发，**从未出现 `repository_dispatch`** | ❌ 端到端从未打通 |

对比同文件的历史可以确认这是重写引入的：旧版本（`9e58c59`，`push` 驱动）在 secret 缺失时是**优雅跳过**（`echo "SKILLS_SYNC_TOKEN not configured; skipping consumer dispatch"`），且 2026-09-15 那次 push 触发的运行是 **success**；新版本（`6077533`）改为**硬失败**（`echo "::error::SKILLS_SYNC_TOKEN is required"`），于是 v1.0.1 的 release 运行暴露了真实的权限缺口。

根因：`SKILLS_SYNC_TOKEN` 是**个人访问令牌**（错误原文如此），且不具备对 `full-aigc-plugins/video-factory-plugin` 的写权限。`repository_dispatch` 要求目标仓的 contents 写权限；若为 fine-grained PAT，还需目标组织 `full-aigc-plugins` 批准该令牌访问。**这不是代码问题，改 workflow 无效。**

修复需人工/组织管理员（本处无法代劳，且 `design.md` 已把「使用本地高权限 OAuth token」列为非目标）：

- 方案一：重建为 fine-grained PAT，选中 `full-aigc-plugins/video-factory-plugin` 并授予 `Contents: Read and write`，再在 `full-aigc-skills/video-factory-skills` 覆盖该 secret
- 方案二：改用对目标仓有写权限的 classic PAT（`repo` scope）
- 方案三（推荐）：改用 GitHub App 安装令牌，避免个人令牌绑定个人生命周期

#### A2 的替代通路已实测可用（这才是 v1.0.2 的实际路径）

由于 dispatch 不可用，须改用插件仓自己的 `workflow_dispatch`。已实测（run `35593155413`，trigger `workflow_dispatch`，16 秒，`success`）：

```bash
gh workflow run skills-sync.yml \
  --repo full-aigc-plugins/video-factory-plugin \
  -f ref=v1.0.1 -f sha=6077533c5dd9c5089998e07c557f6a2d5f6c2203
```

副作用核验（三项全为空/无）：日志出现 `vendored skills already current; nothing to sync`；`chore/skills-sync` 分支未被创建（`git ls-remote` 为空）；未开出任何 sync PR。即**快照与锁一致时该路径幂等无副作用**，可安全用于 v1.0.2。

同时纠正一处对机制的误解：**每日 cron 不能升级版本**。`skill_vendor.py` 仅在传入 `--source-ref` 时改写 `source["ref"]`（见 `cmd_update`：`if package in source_refs: source["ref"] = ...`），而工作流仅在收到 `client_payload.ref` 或 `inputs.ref` 时才追加该参数。

| 触发方式 | 能否把锁升到 v1.0.2 |
|---|---|
| 上游 release dispatch | ❌ 已损坏（403） |
| 每日 cron（03:41 UTC） | ❌ 只按**当前锁定的 ref** 重新校验，不会升级 |
| 手工 `workflow_dispatch` 带 `ref`+`sha` | ✅ **唯一可用通路** |

**结论：v1.0.2 的消费步骤必须包含一次手工 dispatch，不存在「发完 Release 就自动同步」这回事。**

#### A2 复测（同日 11:30 重新授权后）：仍未修复，问题已收敛到源仓 token 本身

授权动作确已发生——源仓 secret 时间戳从 `2026-09-17T10:08:07Z` 变为 `2026-09-21T11:30:00Z`。但以同一路径复测（run `35594549361`，`workflow_dispatch`，8 秒）**依然失败，错误完全相同**：

```
RELEASE_SHA: 6077533c5dd9c5089998e07c557f6a2d5f6c2203
gh: Resource not accessible by personal access token (HTTP 403)
```

复测发生在 secret 更新之后 1 分 57 秒，排除密钥传播延迟。

**隔离测试完成了归因**——用本机凭据（对目标仓有 admin）直接向目标仓发 `repository_dispatch`：

| 环节 | 结果 |
|---|---|
| `gh api --method POST .../dispatches`（本机凭据） | ✅ 成功（exit 0，无 stderr，204 No Content） |
| 目标仓是否收到 | ✅ **收到**——首次出现 `repository_dispatch` 触发的运行（run `35594638252`，`skills-updated`） |
| 该运行下游 | ✅ 干净空操作：`vendored skills already current; nothing to sync`，无 PR，未创建 `chore/skills-sync` 分支 |
| 源仓 secret 中的 token | ❌ 仍无目标仓写权限（403） |

**即：端点、目标仓设置、事件契约、插件侧工作流全部正常，唯一失效的是源仓 `SKILLS_SYNC_TOKEN` 这个 token 自身的权限。**

本处无法代劳修复：铸造任何新凭据（创建 PAT、创建 GitHub App 并下载私钥）都需要浏览器会话；本机 gh 凭据是 OAuth app token（`gho_` 前缀），访问 fine-grained PAT 管理端点返回 404，因此无法枚举或批准待批请求。我虽是 `full-aigc-plugins` 与 `full-aigc-skills` 两个组织的 owner，但 owner 身份不能凭空生成一个可用的令牌。

若要自行修复，fine-grained PAT 须**同时**满足以下四条（任一不满足即复现 403）：

1. **resource owner 不能是错的**——token 必须能覆盖 `full-aigc-plugins`；若创建时 resource owner 选的是 `full-aigc-skills`，它永远够不到目标仓，这是最可能的原因
2. **目标组织须批准**——目标仓属组织所有，需在 `https://github.com/organizations/full-aigc-plugins/settings/personal-access-tokens` 允许 fine-grained PAT 并批准该请求
3. **权限须为 `Contents: Read and write`**——`repository_dispatch` 映射到 Contents 写权限，只读或仅 Metadata 会 403
4. **仓库访问须为 "Only select repositories" 且勾选目标仓**——选 "Public repositories only" 不授予写权限

或改用对目标仓有写权限的 classic PAT（`repo` scope）；推荐长期方案是 GitHub App 安装令牌。

#### 新增风险：目标仓被额外写入了一个同名 secret

复测时发现 `full-aigc-plugins/video-factory-plugin` 也出现 `SKILLS_SYNC_TOKEN`（时间戳 `2026-09-21T11:29:39Z`，此前为空）。该 secret **不是本链路所需**，但会改变插件侧自身行为：

```yaml
token: ${{ secrets.SKILLS_SYNC_TOKEN || secrets.GITHUB_TOKEN }}
```

此前目标仓无此 secret → 回退到 `GITHUB_TOKEN` → 推分支与建 PR 一直成功（历史运行可证）。现在 secret 存在 → 改用它 → **若该 token 对插件仓本身没有 Contents 写权限，一旦出现真实 diff，`chore/skills-sync` 分支推送与 PR 创建会失败**。本轮实测全程走的是 `changed=false` 分支，未触及该代码路径，因此**这一点尚未被验证**。

v1.0.2 首次产生真实 diff 之前必须验证。两条路线：删除目标仓该 secret 以恢复已知可用的 `GITHUB_TOKEN` 回退；或确认该 token 对插件仓有 Contents 写权限。

为支持「同时从 `full-aigc-skills` 与 `full-stack-skills` 两个技能库拉取技能」，已生成两个令牌并配置为下游插件仓的 `FULL_AIGC_SKILLS_SYNC_TOKEN` / `FULL_STACK_SKILLS_SYNC_TOKEN`。实测清点结果：

| 消费端代码 | 全部仍为 `secrets.SKILLS_SYNC_TOKEN \|\| secrets.GITHUB_TOKEN` | ❌ **新 token 是死配置，无任何工作流读取** |

| 推送端代码 | 抽查 6 个库：`full-aigc-skills/{video-factory,image-factory,blender}-skills`、`full-stack-skills/{processon,skills-toolchain}` 读到 `secrets.SKILLS_SYNC_TOKEN`；`full-stack-skills/vue-skills` 未匹配到 secret 行（结构可能不同，需单独核对） | ❌ 均未引用新名 |

**即两个新 token 目前两端都未被使用**，`notify-consumers.yml` 拿到的仍是那个 403 的旧令牌——这正是 11:30 重新授权后复测依旧 403 的原因：改的是旧名字里的值，而失效原因可能在令牌自身的仓库选择/权限上。

#### 多源路由：同组织内已有可照抄的实现

`image-factory-plugin` 的 lock 已有 2 个 source（`full-aigc-skills/image-factory-skills` + `partme-ai/baoyu-skills`），其 `skills-sync.yml` 已实现按 package 路由：

```yaml
      package:
        description: Locked package to upgrade; defaults to image-factory-skills
...
  REQUESTED_PACKAGE: ${{ github.event.client_payload.package || inputs.package || 'image-factory-skills' }}
...
            arguments+=(--source-ref "$REQUESTED_PACKAGE=$REQUESTED_REF")
            arguments+=(--expected-sha "$REQUESTED_PACKAGE=$REQUESTED_SHA")
```

而 `video-factory-plugin` 仍是旧模板：无 `inputs.package`、无 `REQUESTED_PACKAGE`，且把 package 名硬编码为 `video-factory-skills`。lock 层 `skill_vendor.py` 早已支持多 source（`sources` 数组 + `validate_assignment_packages` 按 package 校验），**缺的只是工作流这一层的路由**。

因此「同时从两个技能库拉取」在本仓的补齐方式是同组织内照抄，不是新设计。

#### 由此产生两条路线

**路线一：补全推式（双端都要改）**

- 推送端：把有跨组织写权限的 token 下发到各技能库仓（若意图复用同一对 token，则 `FULL_AIGC_SKILLS_SYNC_TOKEN` → `full-aigc-skills` 各库、`FULL_STACK_SKILLS_SYNC_TOKEN` → `full-stack-skills` 各库），并把 `notify-consumers.yml` 的 `secrets.SKILLS_SYNC_TOKEN` 改为对应新名
- 消费端：`skills-sync.yml` 按来源选 token，并 backport package 路由
- 规模：推送端约 38 个技能库，消费端 23 个插件仓

**路线二：改拉式（只需改消费端）**

- 消费端已持有按来源命名的两个 token，足以自行 clone 上游；自身分支/PR 操作继续用 `GITHUB_TOKEN`（历史运行已证可用）
- 消费端 cron 从「按锁定 ref 重新校验」改为「发现上游最新 release tag 并升级」（`gh api repos/<lib>/releases/latest`），无需任何跨组织写权限
- 推送端 `notify-consumers.yml` 可降级为尽力而为的加速器，或整体退役
- 规模：只改 23 个消费仓，且不再依赖跨组织凭据

**推荐路线二**：消费端本就校验 tag + peeled SHA + 逐技能摘要，拉式不降低安全性；而推式需要给约 38 个库各配一个能写 23 个插件仓的凭据，凭据暴露面显著更大。

**P3 `add-revision-loop-discipline`（补全）**

须回答「循环如何在不破坏人工门的前提下收敛」，落点全部在本仓既有的两块接缝上，不新建机制：

- `src/edit-decision.mjs` 的 `reviseEditDecision` / `diffEditDecision` 已提供镜头级修订原语
- `plan.round` 已是必填字段，且已被绑进报价字段（`src/approval.mjs` 的 `round`/`quoteRevision`），因此「新一轮 = 新 EditDecision + 新报价 + 新批准」天然成立

因此本变更的内容是：

| 项 | 内容 |
|---|---|
| 轮次语义 | 明确一轮的定义；新一轮必然重新报价与重新批准（这是与人工门兼容的唯一形式，须同时写入 harness 契约） |
| 台账扩展 | `job-ledger` 增加跨轮分数历史（当前 `revision` 只数写入次数，不构成轮次） |
| 失速检测 | 移植 dream-loop 判据：最好分数 2 轮内未涨满 1 分，或同一缺口被连续点名 2 次 → 判为「接近失速」，要求改为架构级修改而非继续微调 |
| 升级与终止 | 架构级修改后仍未改善 → 判为「已失速」，停止自动推进并要求人工介入 |
| 回退感知 | 新一轮分数低于上一轮时须显式标记回退，不得被静默接受 |
| 非目标 | **不引入自动重试**——`src/orchestrator.mjs` 的 "automatic retry disabled" 与 `failed segment requires a new round` 保持成立；不改变 rough→人工审→final 节奏 |

**P4 `add-asset-sourcing-ladder`（补全）**

移植 dream-loop 的阶梯结构，但适配本仓的回执制资产模型：

- 阶梯顺序：下载外部资产 → image-to-3D → DCC（本生态首要来源是 blender-design）→ 程序化
- 关键纪律移植：不得因时间/配额压力或自身判断而跳级使用程序化资产
- **必须偏离 dream-loop 的两点**：① 不移植「禁止用 Blender 建模」——本生态 blender-design 是一等资产来源；② 不移植 `fal-batch.mjs` 直连提交——它绕过 `src/approval.mjs` 的报价/批准闸，会制造未授权支出路径
- 分层选型建议可移植（关键资产用强模型、装饰件用轻量模型），但须表达为计划期的成本提示，而非新的计费通道
- 资产登记沿用既有 `asset_manifest.schema.json`
